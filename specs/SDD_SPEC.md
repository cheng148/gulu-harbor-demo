## 1. Objective

### 1.1 建设目标

建设一个移动端优先、具有完整产品观感的“咕噜港”宠物服务Web App/PWA Demo：

- 首页、宠物市场、宠物用品、社区、会员中心和“我的”构成可浏览、可点击的前端原型。
- “AI选宠顾问”是真实实现的多轮对话Agent，能够动态澄清需求、识别硬约束、检索知识、匹配方向与具体宠物，并解释建议。
- 当前Demo用模拟合作商家和模拟在售宠物演示匹配与连接；交易、支付、合同、物流、真实商家沟通等不建设后台能力，相关动作必须提示“Demo演示功能，暂未开放”。
- 用户可以通过链接在手机浏览器中体验；在浏览器和设备支持时，可以把它添加到手机桌面并以Web App方式打开。
- 第一版不建设微信／支付宝小程序，不承诺应用商店安装包、完整离线使用、原生推送或其他原生系统能力。

### 1.2 核心用户

首版核心用户是缺少养宠经验、无法一次说清选宠条件的新手养宠人。繁育者、转让者和资深养宠人只属于历史平台设想，不是首版Agent优化对象。

### 1.3 用户价值

帮助用户从“我想养一只可爱的宠物”逐步走到：

- 看清自己期待怎样相处、能投入多少时间，以及能接受哪些日常负担。
- 区分猫狗过敏、自己明确的绝对底线和可以权衡的偏好。
- 先理解适合的品种/类型方向，再查看模拟合作商家中值得进一步了解的候选宠物。
- 同时看见适合点、负担、风险和不匹配点。
- 在必要时接受“暂不建议养宠”或“先解决前置条件”的诚实结论。

### 1.4 非目标

- 不建设完整电商、支付、合同、物流、账户或长期历史系统。
- 当前Demo不接入真实商家、用户、宠物、订单或交易数据。
- 咕噜港不直接销售宠物，不在Demo中完成真实商家联系、下单或交易。
- 不保证品种或个体的性格、健康和行为。
- 不提供疾病诊断、治疗或替代兽医的建议。
- 不训练或微调模型。
- 不建设全自主、无边界的开放式Agent。
- 不把原策划书中的旧算法、旧技术栈或商业承诺迁入当前实现。

- 匹配等级映射与双层推荐解释
- 条件修改、重新推荐和推荐变化说明

### 2.2 Level B：可交互前端原型

## 3. 产品概念与术语

- Agent：能保存多轮状态、根据当前情况决定下一步，并调用确定性业务能力的对话顾问，不是固定顺序聊天问卷。
- 槽位：画像中的一个结构化字段，例如“是否允许养宠”。
- 硬约束：违反后不能靠其他偏好或高分抵消的条件。
- 品种/类型方向：对更适合哪类宠物的上层建议，可以是品种，也可以是“成年短毛家猫”等类型。
- 候选宠物档案：合作商家提供、可参与匹配的具体宠物记录。当前Demo使用预置的模拟商家与模拟在售宠物；未来可替换为真实合作商家数据。
- 模拟候选宠物：当前Demo数据集中预先存在、明确标注为模拟数据并关联模拟商家的候选档案，不是模型临时生成内容。
- 内部匹配分：仅供排序、测试和评测的0至100数字，不向页面或公共API暴露。
- 匹配等级：用户可见的“很合拍”“值得认识”“需要磨合”。
- 暂不合适：触发过敏或用户明确底线后的排除结论，不是可由软偏好或内部高分抵消的匹配等级，也不进入正式推荐列表。
- 最终建议：关键条件已确认且无未解决阻断项。
- 暂定建议：用户要求直接推荐或非阻断信息未完整确认，必须展示待确认项。
- 暂不建议：当前条件存在无法安全绕过的阻断项，或没有通过硬约束的合理候选。

## 4. 核心用户故事

### US-001 自由表达与增量提取

用户可以用自然语言描述需求。系统提取本轮明确出现的信息，不确定信息保持未知或推断，不得擅自补全。

### US-002 动态追问

系统根据当前画像、阻断项、冲突和候选区分度，每轮选择一个最有信息价值的问题，而不是按固定问卷逐项询问。

### US-003 冲突处理

系统指出互相冲突的要求，解释现实代价，并让用户确认优先级；不得静默忽略任一已确认条件。

### US-004 双层推荐

系统最多展示4个品种/类型方向，并通常从每个入选方向选择1只预置候选宠物，最多4只。当前候选宠物来自模拟合作商家；每张档案必须显示模拟数据说明和“联系商家进一步了解”的Demo入口。前两只表示排序更靠前，后两只是备选；位置不决定匹配等级。候选不足时不得凑数或临时编造。

### US-005 诚实劝退或暂缓

当条件不适合立即养宠时，系统停止购买导向，解释原因并提供可执行的前置准备或替代体验。

### US-006 修改与重算

用户可以修改已确认条件。系统保留其他条件，重新检查冲突、过滤、排序和等级，并说明推荐变化。

### US-007 会话恢复与重置

用户可以在最近成功活动后的24小时内在同一Demo环境恢复会话，也可以主动重置并从空画像开始。

### US-008 完整原型浏览

体验者可以访问所有主要页面，明显按钮均有可理解反馈，未开放业务动作不会伪装为真实成功。

## 5. Agent状态契约

### 5.1 ConversationState

内部状态必须使用明确Schema，禁止使用无约束散乱字典。字段语义如下：

```json
{
  "schemaVersion": "string",
  "conversationId": "string",
  "revision": 0,
  "stage": "NEW|DISCOVERING|RESOLVING_CONFLICT|READY_TO_MATCH|MATCHING|RECOMMENDED|NOT_RECOMMENDED|COMPLETED|EXPIRED|RESET",
  "recommendationMode": "NONE|PROVISIONAL|FINAL",
  "messages": [],
  "profile": {},
  "missingCriticalSlots": [],
  "activeBlockers": [],
  "conflicts": [],
  "questionHistory": [],
  "coreQuestionCount": 0,
  "extraQuestionUsed": false,
  "importantUnknowns": [],
  "acceptedAdjustments": [],
  "consecutiveUnclearTurns": 0,
  "retrievedSourceIds": [],
  "directionCandidates": [],
  "petCandidateIds": [],
  "recommendations": null,
  "safetyFlags": [],
  "createdAt": "date-time",
  "lastActiveAt": "date-time",
  "expiresAt": "date-time"
}
```

约束：

- `revision`从0开始；每次成功消息处理或画像修改后加1。
- `expiresAt = lastActiveAt + 24小时`。创建、成功消息和成功画像修改会刷新；只读请求、失败请求和健康检查不刷新。
- `EXPIRED`和`RESET`为终态，不能继续写入。
- `MATCHING`失败时回到处理前的可恢复状态，不得留下半更新推荐。
- 内部候选允许包含数字分，但公共响应模型不得包含该字段。
- `coreQuestionCount`只统计核心动态问题，最大为3；`extraQuestionUsed`为真后不得再次生成第4个问题。
- `importantUnknowns`只保留可能改变当前前两名或重要等级的未知项；`acceptedAdjustments`必须关联到用户明确接受的具体差距。

### 5.2 SlotValue

每个关键槽位使用统一包裹结构：

```json
{
  "value": "typed value or null",
  "status": "UNKNOWN|INFERRED|CONFIRMED|DECLINED|CONFLICTED",
  "constraintStrength": "HARD|PREFERENCE|UNSET",
  "sourceMessageIds": [],
  "updatedAt": "date-time"
}
```

合并规则：

1. 用户直接、明确表达的值记为`CONFIRMED`。
2. 由含糊语言映射出的值记为`INFERRED`；推断值不能独自满足最终推荐的关键槽位。
3. 用户明确“不确定/不想回答”记为`DECLINED`，不得伪造默认值；可以产生暂定建议，但要列为待确认风险。
4. 新信息与已确认值不一致时记为`CONFLICTED`并进入澄清，不得静默覆盖。
5. 用户通过画像修改接口明确更新时，新值记为`CONFIRMED`，旧冲突关闭并重新计算。
6. `constraintStrength=HARD`表示不可妥协；未明确强度时，安全相关槽位按本规格硬规则处理，外观类默认`PREFERENCE`。

### 5.3 PetPreferenceProfile

首版画像围绕用户本人和宠物的相处关系，至少包含以下槽位；每个槽位继续使用`SlotValue`包裹：

```json
{
  "speciesScope": {},
  "directionAndSizePreference": {},
  "agePreference": {},
  "coatAppearancePreference": {},
  "interactionRhythm": {},
  "companionshipDistance": {},
  "currentTimeArrangement": {},
  "ongoingInvestmentWillingness": {},
  "disturbanceTolerance": {},
  "allergySpecies": {},
  "absoluteBottomLines": {},
  "acceptedAdjustments": {},
  "priorityNotes": {},
  "volunteeredContext": {}
}
```

规则：

- 猫狗偏好决定候选范围，不参与数字加权；“猫狗都行”或未表达时，两个物种均参加排序。
- 品种／类型与体型共同构成一个关联偏好，不能对同一表达重复加分。
- 住房、共同居住者、家庭成员、其他宠物和预算只在用户主动提及时写入`volunteeredContext`，不是默认追问项或FINAL必填项。
- 用户明确“不确定／不想回答”保持未知或拒答；明确“都可以／没有要求”记为已知中立。
- 数组槽位也必须使用`SlotValue`；未知不能用空数组冒充“已确认没有”。

## 6. 状态转换与事务边界

| 当前状态 | 事件 | 条件 | 下一状态 | 必须产生的结果 |
|---|---|---|---|---|
| NEW | 创建成功 | 始终 | DISCOVERING | 欢迎语和一个首问 |
| DISCOVERING | 消息成功 | 出现冲突 | RESOLVING_CONFLICT | 冲突解释和一个澄清问题 |
| DISCOVERING | 消息成功 | 有关键缺失 | DISCOVERING | 一个动态问题 |
| DISCOVERING | 消息成功 | 信息足够 | READY_TO_MATCH | 可立即进入匹配 |
| RESOLVING_CONFLICT | 消息成功 | 冲突未解决 | RESOLVING_CONFLICT | 继续只澄清当前最高风险冲突 |
| RESOLVING_CONFLICT | 消息成功 | 冲突解决但仍缺信息 | DISCOVERING | 下一关键问题 |
| DISCOVERING | 用户要求先推荐 | 无已知物种过敏或明确底线冲突 | MATCHING | 未知按一半权重；若存在影响结果的重要未知则输出PROVISIONAL |
| READY_TO_MATCH | 匹配开始 | 无阻断项 | MATCHING | 状态事务开始 |
| MATCHING | 有合理候选 | 关键槽位完整 | RECOMMENDED | FINAL双层建议 |
| MATCHING | 用户要求先推荐 | 无已知物种过敏或明确底线冲突 | RECOMMENDED | 有重要未知则输出PROVISIONAL，否则可输出FINAL |
| MATCHING | 无合理候选或阻断成立 | 始终 | NOT_RECOMMENDED | 原因和替代行动 |
| RECOMMENDED | 修改画像 | 产生冲突/缺失 | RESOLVING_CONFLICT或DISCOVERING | 旧推荐标记失效 |
| RECOMMENDED | 修改画像 | 仍可匹配 | MATCHING | 重新计算并给变化摘要 |
| 任意可写状态 | 主动结束 | 用户确认结束 | COMPLETED | 保留至过期但不再自动追问 |
| 任意非终态 | 24小时无成功活动 | 始终 | EXPIRED | 后续写请求返回会话过期 |
| 任意非终态 | 主动重置 | 始终 | RESET | 旧会话立即失效 |

一次消息处理是原子操作：画像、问题历史、消息、推荐、`revision`和过期时间要么一起成功，要么全部保持原值。

## 7. 硬约束规则

### 7.1 只认两类硬排除

1. 已确认的猫／狗物种过敏：排除对应物种；不得推荐所谓“绝对低敏”品种绕过。
2. 用户明确说出的绝对底线：排除违反该底线的方向或具体档案。

住房许可、共同居住者、儿童、老人、孕妇、其他宠物和预算不属于首版默认核查事项。用户主动提及时，系统按其原话记录；只有用户明确把某项声明为不可接受时，才成为对应候选的底线。

### 7.2 差距处理

- 时间、互动、陪伴距离、训练、活动、掉毛、叫声、清洁和美容等差距默认参与等级判断，不直接等同于硬排除。
- 关系或生活维度出现0%，且用户尚未接受调整，属于“已确认且未解决的明显差距”，候选标为“需要磨合”。
- 用户明确愿意调整时，对应单项改为75%并附带成立条件；不要求用户证明如何改变，也不能清除其他差距。
- 个人偏好维度的0%只降低排序，不自动形成“需要磨合”。

### 7.3 无结果

- 若所有方向或档案都触发过敏／绝对底线，或在信息充分时内部总分均低于60，正式推荐可以少于4只或为空。
- 页面只说明“按你现在告诉我的条件，还没有特别合适的选择”，并允许用户修改条件；不得评价用户是否有资格养宠。
- 硬排除必须在数字排序前执行，任何高分都不能把候选重新放回正式列表。

## 8. 推荐就绪条件

### 8.1 最少充分信息

系统不要求收集完问题库的全部答案。满足以下任一条件即可进入匹配：

1. 已完成最多3个核心动态问题，剩余未知不会改变当前前两名候选的成员，也不会使重要等级发生变化。
2. 已使用第4个针对性问题，当前证据足以区分正式推荐与需要磨合／暂不合适。
3. 用户明确要求“先推荐”。

正式推荐前必须完成一次猫狗过敏轻量确认；若用户此前已经明确说过则跳过。猫狗方向、偏好和日常条件不要求全部已知。

### 8.2 暂定结果

- 用户要求“先推荐”，或仍存在可能影响当前结论的重要未知时，返回`PROVISIONAL`。
- 未知项内部按该项50%计算，仍保持`UNKNOWN`，不得伪造成已知事实。
- 页面只列出与当前结果有关的待确认项，并说明它可能影响哪一部分结果。
- 用户补充或修改条件后必须重新匹配，不能只改解释文案。

## 9. 动态追问契约

### 9.1 “3+1”问题机制

- 首轮先理解用户自由表达，不要求用户先填表。
- 通常最多提出3个核心问题，每轮只问一个；目标是收集足以判断的信息，不是问完12题。
- 核心问题优先从当前时间情况、期待的相处关系和不能接受的日常负担中选择。
- 问法要温暖、自然、易懂，但不能用卖萌弱化差距或风险。
- 快捷选项只是辅助，必须允许自由输入。

每个问题至少定义`questionId`、`targetSlots`、`fixedOrder`、自然语言模板和快捷选项；Mock使用固定模板，DeepSeek只能润色已经选定的问题，不得自行更换目标槽位。

### 9.2 第4个针对性问题

只有以下情况之一成立才使用第4问：

1. 某个未知项可能使当前前两名中的至少一个被另一方向替换。
2. 某个未知项可能使当前靠前方向进入或离开“需要磨合／暂不合适”。
3. 存在会影响推荐的重要矛盾，或需要确认用户是否愿意为明确偏好调整对应生活条件。

以下情况不使用第4问：

- 前两名成员不变，只是互换顺序。
- 只有第3、第4名等备选内部换位。
- 未知项不会影响展示结果，只影响不展示的内部细节。

第4问最多一次。用户表示愿意调整即可，不继续追问具体改变计划。

### 9.3 稳定与可测试

- 已确认信息不重复问；用户明确修正时更新，重要冲突才澄清。
- 同样状态、问题库版本和候选数据必须选择同一`questionId`。
- LLM负责理解自由文本和自然表达；是否继续提问、是否启用第4问以及选哪个槽位由确定性代码决定。
- 核心问题结束后、正式推荐前进行猫狗过敏确认；已知则跳过。
- 连续两次无法理解时提供改写示例和重置入口，不循环原问法。

## 10. 双层推荐与匹配等级

### 10.1 候选范围和输出数量

- 用户明确只喜欢猫或只喜欢狗时，对应物种成为候选范围；猫狗都行或未描述时，8个方向共同参与。
- “更偏猫但狗也可以”等表达让两个物种都参与，只在同等级同分时作为稳定破同分依据，不单独加权。
- 先对8个方向判断等级并计算内部排序，再依次选择最多4个方向；每个入选方向通常选择1只最靠前的具体档案。
- 方向必须依据方向自身的结构化群体倾向独立评分和定级；具体档案只在其所属入选方向内评分和选择，不得用该方向最高分个体反向代替方向判断。
- 方向入选但其具体档案均被过滤或低于正式展示条件时，只展示方向并说明当前暂无合适个体。
- 前两只是当前排序更靠前的结果，后两只是备选。位置与等级分离，备选也可以是“很合拍”。
- 后位结果不得出现高于前位结果的等级；候选不足时展示更少，不凑数。

### 10.2 内部评分

总分100，只用于内部排序和评测，不代表科学概率：

| 大维度 | 子项 | 分值 |
|---|---|---:|
| 个人偏好 | 品种／类型与体型的关联偏好 | 20 |
| 个人偏好 | 年龄阶段 | 10 |
| 个人偏好 | 毛发／外观 | 10 |
| 相处感觉 | 互动节奏 | 20 |
| 相处感觉 | 陪伴距离 | 10 |
| 日常适配 | 当前时间安排 | 5 |
| 日常适配 | 持续投入意愿 | 15 |
| 日常适配 | 日常打扰接受度 | 10 |

每个子项只取一个比例：

- 100%：明确匹配。
- 75%：小幅差异，或用户已明确愿意为该项调整。
- 50%：未知；状态仍为未知。用户明确“都可以／没有要求”是已知中立，不按未知处理。
- 0%：明确不匹配。

猫狗方向只决定候选范围，不占分。不得根据“非常非常喜欢”等表达热烈程度增加分数；只使用明确比较、范围／排除和愿意调整信息。

### 10.3 匹配等级

先判断信息是否足够，再按以下规则映射：

- `HIGH`／“很合拍”：内部总分80以上，没有未解决的关系／生活明显差距，也没有可能改变主要结论的重要未知。
- `MEDIUM`／“值得认识”：内部总分60至79且没有未解决的明显差距；或存在重要待确认项、小幅差异、用户已接受的成立条件。
- `CAUTION`／“需要磨合”：内部总分不低于60，但关系／生活维度存在0%且用户尚未接受调整。必须说明差距、日常影响以及需要接受或改变什么。
- “暂不合适”：触发猫狗过敏、用户明确底线，或信息充分时内部总分低于60；不进入正式推荐列表。

如果低分主要由未知造成，先继续提问或给暂定结果，不能直接判为“暂不合适”。每个等级必须紧跟具体原因。

### 10.4 排序和展示

1. 先按等级排序：很合拍 > 值得认识 > 需要磨合。
2. 同等级内按内部总分从高到低排序；仍相同再按稳定ID排序。
3. 如果全部展示结果都是“需要磨合”，页面不得写“优先推荐”，而应说明目前没有特别合拍的选择，并展示相对更接近的选项。
4. 页面、公共API和浏览器日志不得包含`matchScore`、`rawScore`或任何0至100精确分，也不得包含模型思维链、系统Prompt、密钥、不存在的档案或无来源的确定性保证。

## 12. 模型提供方与Mock替换边界

### 12.1 统一模型适配器

DeepSeek与Mock实现同一适配器契约，至少覆盖：

- 从本轮文本提取结构化画像增量。
- 将已选定的`questionId`表达为自然问句。
- 将结构化推荐事实转为用户可读解释。
- 对解释执行结构化安全复核。

每个操作都有固定输入Schema、输出Schema、超时、无效输出和失败语义。所有提供方输出都作为不可信数据校验。

推荐解释只接收已经由确定性代码选定的方向与候选事实。模型不得新增、删除或改排候选，不得改变匹配等级，也不得改写为与结构化理由、代价或不匹配点相反的结论。解释输出必须包含一段总体说明，并与输入事实逐项对应；数量不一致视为`MODEL_INVALID_RESPONSE`。

解释产生后必须把总体说明和全部逐项说明一起送入安全复核。总体说明、逐项说明和安全替换中的每段文字都必须非空。安全复核通过后，公共推荐对象才保存`aiNarrative`；若复核拒绝且没有提供数量完全对应的非空安全替换文案，则本轮回滚并返回可重试的`MODEL_INVALID_RESPONSE`。安全替换只能替换文字，不能修改候选、顺序、匹配等级或事实字段。

### 12.2 真人演示

- `MODEL_PROVIDER=deepseek`时调用DeepSeek。
- 模型名通过`DEEPSEEK_MODEL`设置，Gate 1前依据官方文档确认，不在Gate 0凭记忆锁定。
- API Key只来自环境变量。
- 超时、限流、鉴权失败和Schema无效都不能产生伪造推荐。
- 空内容、截断、无效JSON、错误响应外壳或错误Schema最多自动重试一次，即同一次模型操作最多发出两次相同请求。
- 超时、网络错误、HTTP错误和鉴权失败不在适配器内自动重试，由公共API返回可重试错误，避免结果不明确时产生重复调用和额外费用。
- 模型失败时保留处理前状态，返回可重试错误。

### 12.3 自动化测试

- 自动化测试强制`MODEL_PROVIDER=mock`。
- Mock对同一场景、同一输入和同一调用序列返回字节级稳定的结构化结果。
- Mock不得访问网络、读取DeepSeek Key或按随机数变化。
- 测试启动时如果检测到真实提供方或网络模型调用，测试立即失败。
- Mock夹具按场景ID和调用步骤维护，不通过复制整段最终页面文案来绕过业务逻辑。

### 12.4 Mock只替换什么

Mock只替换语言模型的结构化理解与自然语言生成。以下能力必须使用与真人演示完全相同的真实代码路径：

- 输入边界校验
- 会话持久化、24小时过期和重置
- 槽位合并与`revision`控制
- 冲突检测
- 问题优先级和`questionId`选择
- 推荐就绪判断
- 知识检索接口与本地知识数据
- 硬约束过滤
- 内部评分、稳定排序和等级映射
- 双层推荐组装
- 安全规则
- API请求与响应Schema
- 错误映射

## 13. API通用契约

### 13.1 基本约定

- 基础路径：`/api/v1`
- JSON字段：camelCase
- 时间：带时区的ISO 8601 UTC字符串
- ID：服务端生成的不透明字符串
- 所有请求和第三方响应在边界校验
- 公共响应不暴露内部数字分、Prompt、栈信息或密钥
- 写请求使用`baseRevision`避免旧页面覆盖新状态
- 发送消息使用`clientMessageId`保证重复提交幂等

成功响应：

  "meta": {
    "requestId": "string"
  }
}
```

错误响应：

    "message": "用户可理解的信息",
    "retryable": false,
    "details": {}

    "requestId": "string"

}
```

## 14. API端点

### 14.1 创建会话

`POST /api/v1/conversations`

请求：

```json
{
  "clientLocale": "zh-CN"
}
```

`clientLocale`可省略，首版只接受`zh-CN`。

成功：`201 Created`

```json
{
  "data": {
    "conversation": {},
    "assistantMessage": {},
    "nextQuestion": {
      "questionId": "ask-current-time",
      "text": "string",
      "quickReplies": []
    }
  },
  "meta": {
    "requestId": "string"
  }
}
```

验收：创建后`revision=0`、`stage=DISCOVERING`、画像全为未知、`expiresAt`为创建时间后24小时。

### 14.2 发送消息

`POST /api/v1/conversations/{conversationId}/messages`

请求：

```json
{
  "clientMessageId": "client-generated-unique-id",
  "baseRevision": 0,
  "content": "用户文本",
  "quickReplyId": null
}
```

约束：

- `content`去除首尾空白后为1至2000个Unicode字符。
- `quickReplyId`可空；存在时必须等于当前响应`quickReplies`中的某个完整字符串。首版用该字符串本身作为快捷选项标识，不另设隐藏ID。
- 相同会话和`clientMessageId`重复提交返回第一次成功结果，不重复增加消息、轮次或刷新两次状态。
- `baseRevision`不等于服务端当前值时返回`409 REVISION_CONFLICT`。

成功：`200 OK`，返回：

```json
{
  "data": {
    "conversation": {},
    "assistantMessage": {},
    "profileChanges": [],
    "nextQuestion": null,
    "quickReplies": [],
    "recommendation": null,
    "warnings": []
  },
  "meta": {
    "requestId": "string"
  }
}
```

`nextQuestion`和`recommendation`最多一个非空。推荐对象遵守第15节，不能含内部分数。

### 14.3 获取会话

`GET /api/v1/conversations/{conversationId}`

成功：`200 OK`，返回公共会话摘要、可展示消息、当前问题和当前推荐；只读请求不刷新24小时期限。

```json
{
  "data": {
    "conversation": {},
    "messages": [],
    "currentQuestion": {},
    "recommendation": null
  },
  "meta": {
    "requestId": "string"
  }
}
```

新会话的欢迎语作为第一条可展示消息返回；`currentQuestion`沿用创建会话的公共问题结构。响应不得包含内部Prompt、来源消息ID、候选内部ID或任何数字匹配分。

### 14.4 修改画像

`PATCH /api/v1/conversations/{conversationId}/profile`

请求：

```json
{
  "baseRevision": 3,
  "updates": {
    "interactionRhythm": {
      "value": "HIGH",
      "constraintStrength": "PREFERENCE"
    }
  }
}
```

规则：

- 只接受白名单槽位和合法值。
- 用户修改值记为`CONFIRMED`。
- 成功后`revision+1`并刷新24小时期限。
- 旧推荐立即失效；服务端同步重新判断：信息足够时重新匹配，信息不足或仍有冲突时只返回下一澄清问题，不得过早生成推荐。
- 返回`profileChanges`和`recommendationChanges`，说明新增、移除、等级变化或转为暂定。

### 14.5 获取推荐

`GET /api/v1/conversations/{conversationId}/recommendations`

- `RECOMMENDED`或`NOT_RECOMMENDED`时返回`200`。
- 尚未形成建议时返回`409 RECOMMENDATION_NOT_READY`。
- 响应只包含公共推荐模型，不含数字分。

### 14.6 主动重置

`DELETE /api/v1/conversations/{conversationId}`

- 成功返回`204 No Content`。
- 旧会话立即标记`RESET`且不可恢复。
- 前端随后显式调用创建会话接口；服务端不暗中复用旧ID。
- 重复删除已经重置的会话仍返回`204`，保证幂等。
- 重置后的旧ID用于读取或写入时返回`404 CONVERSATION_NOT_FOUND`。

### 14.7 健康检查

`GET /health`

返回服务存活和必要依赖的非敏感状态，不返回模型名、Key、环境变量值或内部路径。

## 16. HTTP错误语义

| HTTP | code | retryable | 场景 |
|---|---|---|---|
| 400 | INVALID_REQUEST | false | JSON结构错误 |
| 404 | CONVERSATION_NOT_FOUND | false | ID不存在或已重置 |
| 409 | REVISION_CONFLICT | true | 客户端版本落后 |
| 409 | RECOMMENDATION_NOT_READY | false | 尚未形成推荐 |
| 410 | SESSION_EXPIRED | false | 24小时无成功活动 |
| 422 | VALIDATION_ERROR | false | 文本为空、超长或字段语义非法 |
| 422 | INVALID_QUICK_REPLY | false | 快捷选项不属于当前问题 |
| 429 | RATE_LIMITED | true | 模型或服务限流 |
| 502 | MODEL_INVALID_RESPONSE | true | 提供方响应未通过Schema |
| 503 | MODEL_UNAVAILABLE | true | 模型超时或不可用 |
| 503 | KNOWLEDGE_UNAVAILABLE | true | 必要知识源无法读取 |
| 500 | INTERNAL_ERROR | true | 未分类服务错误 |

模型或知识错误不得提交半成品状态；重试使用原`baseRevision`。

## 17. 前端信息架构与核心反馈

### 17.1 路由

- `/`：首页
- `/choose`：AI选宠顾问
- `/choose/result/[conversationId]`：推荐结果
- `/pets`和`/pets/[id]`：宠物市场与详情
- `/supplies`：宠物用品
- `/community`和`/community/[id]`：社区与帖子详情
- `/membership`：会员中心
- `/me`：我的

### 17.2 AI选宠页

必须包含：

- 对话区、快捷回复和自由输入
- 当前已确认画像与待确认项
- 可理解的处理中、失败和可重试状态
- 修改条件入口
- “重新开始”入口和重置确认
- 24小时保存说明和准确过期时间
- 建议边界与隐私提示

页面不得暴露模型思维链、系统Prompt、内部数字分或API Key。

### 17.3 结果页

必须清晰分区：

1. 当前结论与最终/暂定/暂不建议状态
2. 品种/类型方向
3. 候选宠物档案、模拟商家与模拟在售说明
4. 待确认项、风险和修改条件入口

匹配等级不能只靠颜色，必须有文字。方向与具体个体的证据口径要可辨认。

### 17.5 会员中心与“我的”原型

- `/membership`只提供“月度会员／年度会员”两种不含价格的模拟套餐选择；价格、正式权益和付费规则尚未确认，不得自行承诺。
- 用户可以在本机切换“普通状态／会员展示状态”，用于检查两种页面外观；该状态必须明确标注为Demo预览，不代表已经开通会员。

## 20. TDD与测试策略

### 20.1 强制顺序

每项业务行为遵循：

1. 在规格中存在明确规则和验收标准。
2. 编写表达该行为且因功能缺失而失败的测试。
3. 确认失败原因与预期一致。
4. 编写最小实现使测试通过。
5. 重构并运行相关测试和全量验证。
6. Bad Case修复必须补回归测试。

### 20.2 测试层级

- 单元测试：槽位合并、冲突检测、问题排序、硬过滤、内部评分、等级映射、TTL和Schema。
- 模型契约测试：DeepSeek适配器和Mock遵守同一输入输出Schema；自动化不调用真实网络。
- Agent集成测试：多轮状态、跳问、直接推荐、知识检索、双层推荐、条件修改和失败回滚。
- API契约测试：状态码、公共字段、幂等、revision冲突、过期和重置。
- 前端测试：导航、按钮反馈、匹配等级、无精确分、错误和重置。
- 端到端测试：首页进入选宠，完成5轮以上动态对话，查看双层建议，修改条件并重新推荐。
- 评测：至少24条固定对话案例，保留输入、期望、实际、指标、日期和Bad Case。

## 21. 可测试验收标准

以下均为后续实现与验收目标，不代表当前已实现。

### AC-001 跳过已知信息

- Given：用户首轮已经说明工作日独处时间、期待的互动方式和不能接受掉毛。
- When：系统选择核心问题。
- Then：不重复询问这三项，只从仍可能影响结果的未知中选择下一问。

### AC-002 动态分支不同

- Given：两个用户都只说“想养只狗”；A补充“每天时间很少”，B补充“时间充足但希望宠物不要太黏”。
- When：系统选择下一问。
- Then：A和B的目标槽位及`questionId`不同，且都不是固定问卷的下一题。

### AC-003 “3+1”上限

- Given：问题库仍有多个未知槽位。
- When：已完成3个核心问题且没有满足第4问条件。
- Then：不再继续追问，进入匹配；`coreQuestionCount=3`且`extraQuestionUsed=false`。

### AC-004 第4问触发边界

- Given：场景A中一个未知答案可能替换当前前两名成员；场景B只可能让前两名互换顺序；场景C只影响备选内部顺序。
- When：评估是否追加问题。
- Then：只有A使用第4问；B、C直接进入匹配。

### AC-005 已确认值与修正保护

- Given：用户已明确喜欢互动积极的宠物，随后明确修正为更喜欢安静陪伴。
- When：模型同时返回旧推断。
- Then：新明确表达覆盖旧值，模型推断不得覆盖用户修正；若只是前后含糊冲突则标记`CONFLICTED`。

### AC-006 过敏最后确认

- Given：核心问题已经结束且过敏信息未知。
- When：准备正式推荐。
- Then：先提出一次猫狗过敏轻量确认；如果用户此前已明确无猫狗过敏，则跳过该问题。

### AC-007 物种过敏排除

- Given：用户确认对猫过敏、对狗不过敏。
- When：执行推荐。
- Then：所有猫方向不进入正式推荐，狗方向仍可参与；解释中不得用“低敏猫”绕过排除。

### AC-008 用户绝对底线

- Given：用户明确说“完全不能接受明显掉毛”。
- When：候选方向或档案的已知掉毛负担违反该底线。
- Then：候选在数字排序前排除，其他偏好高分不能抵消。

### AC-009 未知按一半权重

- Given：某子项未知，另一个用户明确说该项“都可以”。
- When：计算内部排序。
- Then：未知项按该项50%计算并保持`UNKNOWN`；“都可以”记为已知中立，不标为待确认。

### AC-010 先推荐与待确认

- Given：用户在核心信息尚未完全稳定时要求“先推荐”。
- When：没有已知过敏或绝对底线阻止全部候选。
- Then：返回`PROVISIONAL`；只列可能影响当前结果的待确认项，不伪造完整画像。

### AC-011 两层推荐与数量

- Given：至少4个方向各有合格具体档案。
- When：推荐完成。
- Then：最多返回4个方向和4只宠物，通常每个方向1只；每只关联现有`directionId`与数据集`petId`。

### AC-012 候选不足不凑数

- Given：只有2只具体档案通过底线和最低分规则。
- When：推荐完成。
- Then：只返回2只，不放宽条件、不编造其余档案。

### AC-013 无合适候选

- Given：全部候选触发已知底线，或信息充分时总分都低于60。
- When：推荐完成。
- Then：正式宠物列表为空，说明当前没有特别合适的选择并允许修改条件；不评价用户是否有资格养宠。

### AC-014 不暴露精确分

- Given：内部已经计算0至100分。
- When：获取消息、会话或推荐API，或渲染结果页。
- Then：JSON、日志和页面不存在`matchScore`、`rawScore`或精确匹配数字，只展示匹配等级和原因。

### AC-015 等级映射与排序

- Given：A为82分且无明显差距或重要未知；B为76分且无明显差距；C为85分但关系维度有未解决0%；D触发过敏；E为58分且信息充分。
- When：映射等级并排序。
- Then：A为“很合拍”，B为“值得认识”，C为“需要磨合”，D和E为“暂不合适”且不进入正式列表；正式结果先按等级、再按同等级内分数排序。
- And：每个等级说明具体原因；如果展示项全部是“需要磨合”，页面不得使用“优先推荐”。

### AC-016 愿意调整与重算

- Given：候选因活动投入与用户当前生活冲突而为0%，用户明确说愿意为该项调整。
- When：重新计算。
- Then：只把该项改为75%并附带成立条件；不追问具体改变计划，不清除其他冲突，结果按新等级和分数重新排序。

### AC-017 消息幂等

- Given：同一`clientMessageId`成功提交两次。
- When：第二次到达。
- Then：返回第一次结果；消息数、`revision`和状态只变化一次。

### AC-018 Revision冲突

- Given：服务端`revision=4`，客户端提交`baseRevision=3`。
- When：执行写请求。
- Then：返回`409 REVISION_CONFLICT`，状态不变。

### AC-019 24小时滑动过期

- Given：会话在T0创建，T0+20小时成功发送消息。
- When：读取过期时间。
- Then：`expiresAt`更新为该成功消息时间后24小时；只读请求不延长。

### AC-020 会话过期

- Given：最近成功活动超过24小时。
- When：继续发送消息。
- Then：返回`410 SESSION_EXPIRED`，状态不变，前端提供新建会话入口。

### AC-021 主动重置

- Given：已有画像和推荐。
- When：调用重置。
- Then：返回204；旧ID不可读写；新建会话画像为空且不继承旧数据。

### AC-022 Mock确定性

- Given：相同夹具、输入和调用序列重复运行两次。
- When：使用Mock。
- Then：结构化输出一致，不访问网络，不读取或消耗DeepSeek Key。

### AC-023 Mock边界真实

- Given：Mock返回画像增量。
- When：完成推荐流程。
- Then：槽位合并、冲突、问题选择、知识检索、过滤、评分、等级和API Schema均走生产同路径。

### AC-024 模型失败回滚

- Given：消息处理前`revision=2`。
- When：DeepSeek超时或返回无效Schema。
- Then：返回对应可重试错误；`revision`、消息、画像、推荐和过期时间保持处理前值。

### AC-025 知识无结果

- Given：必要知识检索在一次受控的扩大查询后仍无结果。
- When：生成推荐。
- Then：不提交推荐和状态变更；返回`503 KNOWLEDGE_UNAVAILABLE`，不编造来源、方向或具体档案。

### AC-026 连续无法理解

- Given：连续两轮输入都无法映射到当前问题。
- When：第二次失败。
- Then：提供改写示例和重置入口，不无限重复原问题。

### AC-027 原型边界

- Given：用户点击支付、合同、物流、发帖或会员确认。
- When：动作触发。
- Then：显示“Demo演示功能，暂未开放”，不创建真实业务数据。

### AC-028 五轮动态演示

- Given：一个信息不足的新手场景。
- When：完成至少5轮对话。
- Then：问题随状态变化、已知项被跳过、至少处理一个硬约束或冲突，并形成FINAL、PROVISIONAL或NOT_RECOMMENDED之一。

### AC-029 候选档案与模拟商家边界

- Given：推荐返回一只候选宠物。
- When：校验公共响应和结果页。
- Then：`petId`与`merchantId`均存在于预置数据；页面显示“Demo模拟数据，不代表真实在售”和“联系商家进一步了解”；点击后只显示暂未开放，不创建订单、支付或真实商家会话。
- And：DeepSeek或Mock返回不存在的宠物或商家ID时，结构校验失败且不提交推荐。

### AC-030 移动端Web App/PWA边界

- Given：用户使用受支持的手机浏览器访问第一版Demo。
- When：打开首页并完成添加到桌面的流程。
- Then：可以从手机桌面图标再次打开Web App，并完成AI选宠对话、查看结果、修改条件和重置。
- And：页面和说明不把第一版描述为小程序、应用商店原生App或完整离线App；浏览器或设备不支持安装时，仍可通过链接完成核心体验，并给出普通浏览器访问说明。

### AC-031 主流程推荐解释与安全复核

- Given：确定性逻辑已经生成排序固定的双层推荐，模型返回与每项事实一一对应的解释，并且安全复核通过。
- When：主消息API提交本轮推荐。
- Then：公共推荐保留原方向、宠物、顺序和匹配等级，并额外返回安全复核后的`aiNarrative`；自动化测试使用Mock完整经过相同路径。
- Given：解释数量与事实数量不一致，或安全复核拒绝且没有完整安全替换文案。
- When：主消息API准备提交推荐。
- Then：返回可重试的`MODEL_INVALID_RESPONSE`，本轮消息、画像、推荐、revision和24小时期限均不写入。

## 22. 固定评测集最低覆盖

至少24条案例，必须覆盖：

1. 初始表达已经包含大量条件，系统跳过已知项。
2. 初始表达极少，系统进入动态提问。
3. 两个相似首轮输入因不同回答选择不同下一问。
4. 完成3个核心问题后结果稳定，不追加第4问。
5. 未知会替换前两名成员，追加第4问。
6. 前两名只互换顺序，不追加第4问。
7. 只改变备选顺序，不追加第4问。
8. 用户主动要求先推荐，输出暂定结果。
9. 过敏未知，在正式推荐前最后确认。
10. 过敏已知，跳过重复确认。
11. 猫过敏只排除猫方向。
12. 狗过敏只排除狗方向。
13. 用户明确掉毛绝对底线。
14. 用户明确叫声绝对底线。
15. 未知项按50%且保持未知。
16. “都可以／没要求”按已知中立处理。
17. 强烈语气不额外加偏好分。
18. 猫狗范围不占数字权重。
19. 品种与体型关联，不重复加分。
20. 用户愿意调整某一冲突，该项变为75%。
21. 愿意调整不清除其他冲突。
22. 很合拍、值得认识、需要磨合、暂不合适四种结论边界。
23. 同等级内按数字分排序，公共结果不泄漏数字分。
24. 备选仍可以是“很合拍”。
25. 全部展示为“需要磨合”时不使用“优先推荐”。
26. 候选不足4只时不凑数。
27. 信息充分且全部低于60时不正式推荐。
28. 8个方向均能映射到2个预置模拟候选档案和对应模拟商家，且不临时编造。
29. DeepSeek超时或结构无效时事务回滚。
30. Mock不访问网络并复用生产业务路径。
31. 会话24小时过期。
32. 用户主动重置。
33. 候选档案展示模拟来源、模拟在售状态和联系商家Demo边界。
34. 支持的手机浏览器可以添加Web App到桌面并完成核心流程。
35. 不支持安装时仍可通过链接使用，且不出现小程序或原生App上架误导。

## 24. 失败与降级

- DeepSeek不可用：保留处理前状态，提示重试，不伪造推荐。
- 模型结构无效：校验失败并返回可重试错误，不让自由文本绕过业务Schema。
- 知识无结果：先执行一次受控的扩大查询；仍无结果则回滚本轮推荐事务并返回`KNOWLEDGE_UNAVAILABLE`，前端可另行展示不依赖推荐结论的通用准备建议。
- 无符合候选：解释哪些硬约束排除了候选，允许用户修改，但不施压放宽。
- 输入无法理解：先改写澄清；连续两次后提供示例和重置。
- 会话过期：不恢复旧状态，提供创建新会话入口。
- 前端接口失败：显示可重试状态，不能无限加载。
- 推荐解释安全复核失败：不发布未复核文案，返回安全降级模板或可重试错误。

## 25. 安全、隐私与外部输入

- API Key只存在于环境变量和部署密钥，不提交真实Key。
- 不主动收集身份证、支付信息、精确住址、手机号或详细医疗记录。
- 用户输入、模型输出和外部知识均按不可信内容处理并在边界校验。
- Prompt注入不能修改硬约束、工具权限、系统边界或公共Schema。
- 不展示内部Prompt、思维链、服务器栈或敏感配置。
- 宠物健康内容只提供一般风险提示和线下专业咨询建议。
- 24小时保存是Demo可用性设计，不是账户级隐私保险；公开演示前必须清理会话数据。

## 26. 视觉与可用性底线

- 视觉方向为温暖、可信、有生命感的“海港宠物顾问”，避免模板化商城。
- AI选宠入口是首页最清晰的主行动点。
- 不使用默认Inter、Arial或system字体作为主视觉字体。
- 移动端是第一版主要体验和验收场景；桌面端仍能完成对话、查看两层结果、修改条件和重置。
- 在支持的移动浏览器中提供添加到桌面的Web App/PWA体验；不支持时不得阻断链接访问。
- 关键状态不能只依赖颜色；键盘焦点、文本对比度、图片替代文本满足基本无障碍要求。
- 完成页面后必须在真实浏览器检查导航、响应式、控制台和网络错误。
- UX-01视觉基准采用用户在2026-08-11最终选定的“港湾手账”换色前原版：温暖纸张底色、海港插画、猫狗与灯塔意象、深海军蓝主按钮、手写感标题和底部导航；不得自行换成已放弃的三套配色。

## 27. Always / Ask First / Never

### Always

- 开始工作前读取`PROJECT_CONTEXT.md`和本规格。
- 业务行为变化先修订规格。
- 核心行为按TDD实现并保留证据。
- 区分已设计、已编码、已运行、已测试和已部署。
- 区分真实Agent、原型交互和暂未开放功能。
- 对外推荐只展示等级，不展示精确分。

### Ask First

- 修改核心用户、猫犬范围或双层推荐结构。
- 修改硬约束、匹配等级阈值或24小时会话规则。
- 增加账户、支付、真实交易、真实数据或显著API成本。
- 使用外部图片素材。
- 选择页面原型制作工具或使用需要登录、上传内容的外部设计平台。
- 修改已批准的页面结构、主要操作流程或视觉方向。
- 创建公开仓库或部署。

### Never

- Gate 0批准前生成实施计划、任务或生产代码。
- 提交API Key。
- 用真实用户、商家、宠物或交易数据填充Demo。
- 让Mock替换业务逻辑或用Mock成绩冒充真人模型成绩。
- 用软分抵消硬约束。
- 编造具体宠物档案或知识来源。
- 输出医疗诊断、品种保证或绝对低敏承诺。
- 把原型动作描述为真实后台能力。
- 为通过检查删除失败测试。
- 未经批准发布。
