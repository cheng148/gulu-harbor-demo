## 2026-08-13：T28接口类型与浏览器会话边界

- 前端接口类型由后端提交到仓库的OpenAPI快照生成，锁定`openapi-typescript` 7.12.0；总验证使用检查模式阻止“后端接口已变化、前端类型未更新”的提交。
- 前端统一API客户端只处理公共会话接口和统一错误格式，不保存、不发送DeepSeek Key；Key只能留在后端环境变量中。
- 浏览器本地只保存`conversationId`和`expiresAt`。记录过期、格式损坏或出现额外字段时立即清除，完整画像和消息仍以后端SQLite为准。
- 生成的TypeScript类型提供开发期字段约束，不宣称能单独验证真实网络响应；运行时异常继续由公共错误契约与后续浏览器流程测试覆盖。

## 2026-08-14：T33 DeepSeek适配器边界

- 状态：T33已按TDD完成；这不是T35真人模型演示完成记录。
- 使用DeepSeek当前OpenAI兼容`/chat/completions`接口，默认模型为`deepseek-v4-flash`，模型名仍由`DEEPSEEK_MODEL`配置；接口地址必须使用HTTPS。
- 请求采用非流式JSON Output，提示中明确要求JSON并附输出Schema；显式关闭thinking，不处理或保存推理内容。默认超时30秒，可由`DEEPSEEK_TIMEOUT_SECONDS`调整。
- DeepSeek和Mock复用四类输入输出Schema及两项语义保护：画像增量只能指向本轮消息，模型不能更换确定性规则选中的问题或快捷选项。过滤、评分、等级和排序仍不交给模型。
- DeepSeek响应作为不可信外部数据处理：响应外壳、结束原因、非空内容、JSON和业务Schema逐层校验；错误信息不回显Key或提供方响应正文。
- T33自动化全部使用假HTTP响应，不访问DeepSeek、不产生费用。无效响应后的最多一次受控重试、事务回滚和TTL保护属于T34，不在T33中提前实现。
- 官方依据：[DeepSeek Chat Completion](https://api-docs.deepseek.com/api/create-chat-completion)、[JSON Output](https://api-docs.deepseek.com/guides/json_mode/)、[Thinking Mode](https://api-docs.deepseek.com/guides/thinking_mode)、[HTTPX超时](https://www.python-httpx.org/advanced/timeouts/)、[HTTPX MockTransport](https://www.python-httpx.org/advanced/transports/)。

## 2026-08-14：T34受控重试与失败回滚边界

- 状态：T34已按TDD完成；这不是T35真人模型演示完成记录。
- 空内容、截断、无效JSON、错误响应外壳或错误业务Schema统一视为`INVALID_OUTPUT`，对同一次模型操作最多立即重试一次，即最多发出两次相同请求。
- 超时、网络错误、HTTP错误和鉴权失败不在适配器内自动重试。原因是这类失败无法可靠判断提供方是否已经处理请求，自动重复可能增加延迟、重复调用和费用；公共接口仍返回可重试错误，由用户决定是否重试整轮。
- 模型处理发生在会话写入之前。只有本轮全部成功后才一次性写入SQLite；两次无效响应或超时不会提交revision、消息、画像、推荐、TTL或成功幂等记录。
- 自动化使用`httpx.MockTransport`和本地SQLite验证，不读取真实Key、不访问DeepSeek、不产生费用。

## 2026-09-06：模型只负责语言，确定性代码负责决定

- 状态：已批准并已实现。
- 背景：自然语言需要模型理解，但过敏、明确底线、追问选择和推荐排序必须能够稳定测试。
- 决定：模型只执行画像提取、问题措辞、推荐解释和安全复核四类操作；硬约束、冲突、3+1问题边界、下一问、候选过滤、评分、等级和排序均由确定性代码执行。
- 放弃的方案：让模型自由决定下一问与推荐。原因是同一输入可能得到不同决定，无法证明硬约束始终优先，也难以复现Bad Case。
- 影响：语言更自然，同时核心判断可回归；代价是需要维护明确Schema、规则和模型边界。

## 2026-09-06：自动化使用Mock，真人演示使用DeepSeek

- 状态：已批准并已实现。
- 背景：如果自动测试直接调用DeepSeek，会消耗额度、受网络影响，而且模型回答变化会让测试忽好忽坏。
- 决定：确定性Mock和DeepSeek实现同一组模型接口；自动化测试强制使用Mock，真人演示才使用DeepSeek。
- 放弃的方案：用真实模型跑每一次测试。原因是结果不可重复、费用和网络不可控，也容易把“模型这次答对”误当成规则正确。
- 影响：测试能稳定证明业务规则；Mock成绩不能冒充真人模型成绩，两类证据必须分开记录。

## 2026-09-06：SQLite是唯一服务端会话真相

- 状态：已批准并已实现。
- 背景：浏览器、LangGraph和数据库如果各存一套完整会话，恢复、过期、重复提交和冲突时会不知道该相信谁。
- 决定：完整会话只写入SQLite；浏览器只保存会话ID和到期时间；LangGraph不使用checkpointer另存状态。成功轮次通过版本号和幂等ID一次提交，重置后旧会话写入墓碑。
- 放弃的方案：浏览器保存完整画像，或让LangGraph checkpointer与SQLite并存。原因是会形成多份互相可能不一致的状态。
- 影响：首版恢复和回滚逻辑清楚、部署简单；SQLite适合当前小规模Demo，但不代表未来多人高并发仍沿用同一部署方式。

## 2026-09-06：公共结果展示等级，不展示内部数字分

- 状态：已批准并已实现。
- 背景：内部数字用于同等级排序，但不具备科学概率含义；对外展示容易让用户误解为精确的适配率。
- 决定：公共API和页面只展示“很合拍、值得认识、需要磨合、暂不合适”、理由、代价、不匹配点和待确认项；内部数字只用于排序与评测。
- 放弃的方案：显示类似“匹配度82%”。原因是它会制造错误精确感，也无法保证具体个体一定符合品种群体倾向。
- 影响：用户看到的解释更诚实；内部仍可用数字稳定比较，但必须通过契约测试防止泄漏。

## 2026-09-06：平台外壳采用可点击原型，AI选宠是唯一做深核心

- 状态：已批准并已实现。
- 背景：第一版需要让用户理解完整产品方向，但同时实现真实电商、社区和会员后台会严重扩大范围。
- 决定：首页、市场、用品、社区、会员中心和“我的”做成高质量可点击原型；多轮AI选宠、会话状态和匹配链路真实实现。所有未开放业务动作统一显示Demo提示。
- 放弃的方案：为了看起来完整而补建真实支付、订单、物流、发帖、账户和会员后台。原因是这些能力不验证当前核心假设，并会分散开发与测试投入。
- 影响：Demo可以展示完整产品外壳，同时对外必须明确哪些是原型、哪些已编码、哪些已测试、哪些尚未部署。
